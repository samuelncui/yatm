# User interface

Status: Current v1 development architecture.

The browser application: routes, browsers, dialogs, selection models and presentation.
[APIs and services](api.md) owns the endpoints it calls, the
[command-line interface](cli.md) owns the scripted surface over the same operations, and
[Interface contracts](contracts.md) owns the rules shared across them, which this
document does not restate.

**The target environment is one machine or a local network, and this application is
local software rather than a typical web service.** The server reads the same
filesystem the operator browses, over a connection measured in hundreds of megabits
per second at worst, so payload size is never a reason to split a listing, to defer
rows, or to degrade a stated fact into an estimate. A response of the size one
directory produces is not a design constraint here; a slow or partial answer presented
as a complete one is.

**Every file list follows the local file browser model.** Opening a directory presents
that directory as one complete, sorted list, and it shows the total up front: the
operator's first look answers "how many entries are here", never "100 rows, unknown
remainder". One visit reads the directory once. After enumeration and sorting, the pane
publishes projected batches as they arrive, so the first rows and the total are on
screen while later rows' metadata is still being read, and the pane keeps saying it
is reading until the last batch settles. Scrolling or rendering a later part of
the list must not re-read it, and the list must not present a moving count while the
directory it describes is unchanged by the operator's own actions. A listing is updated
by the operator's own actions and by an explicit **Refresh**; it does not watch the
filesystem or refresh itself. Where a total is genuinely unknown - a search whose matches
are not counted - the interface shows the count as unknown instead of a number that
describes only what has loaded. This is the contract for every surface that lists files,
whether the rows come from the catalog or from a live filesystem directory. A query is
not a directory listing and keeps its own paged form.

## State and Styling

Each fact has one owner. Redux stores shared application state; it does not replace the router,
controlled forms or request lifetimes.

| State | Owner and lifetime |
| --- | --- |
| Archive/Restore selections and Restore version policy | Application Redux store; hydrate browser-session preferences once, then persist changes. Successful submission clears only the submitted revision, preserving later edits. |
| Committed Library/Preview Settings | Application Redux store; only a current Get or successful Save publishes values. Older reads cannot replace a Save, and an initial failure leaves values unknown. Editors keep local drafts. |
| Jobs return position, loaded rows, revisions and tombstones | In-memory Redux snapshot per route filter; request lifetimes remain local and late responses cannot publish after leaving. |
| Navigation and active route filters | Router. |
| Panes, sparse Identical pages, log/result windows, dialog drafts and pending actions | The owning view or shared feature hook; discard or invalidate them when their request or source changes. |

The [application state module](../../frontend/src/state/store.ts) uses serializable protobuf JSON
and memoized decoded selectors. Controllers, timers and in-flight promises remain outside Redux.
Committed Settings and Job snapshots are not persisted. Browser storage is an optional preference
boundary: failed reads use the established default, and failed writes cannot turn a successful
server operation into a failure. A preference retains its own commit rule, such as a confirmed
Restore destination or successful Scan submission; merely editing a draft does not persist it.

Instants follow the [shared time contract](contracts.md#time-values). Decoded values remain
`bigint`; serializable state uses decimal strings. [Shared date helpers](../../frontend/src/tools/time.ts)
convert to `Date` only for display and date controls, with range validation and correct rounding
before the Unix epoch. An unchanged Restore cutoff keeps its original nanoseconds rather than
round-tripping through the control's lower precision.
File rows keep their original nanoseconds as the shared browser date-sort key; saved-version
ordering and Preview selection follow the Library's [latest saved version order](library.md#organization-and-content)
with exact nanosecond comparisons. A first-date display fallback does not replace an unknown last archive date in that order.

Shared read hooks keep requests local to each consumer. Preview and saved-version reads share their
feature hooks; the [Location-choice hook](../../frontend/src/components/use-location-choices.ts) owns
the root menu, Library filters, Restore, Locate original and Identical scope's append-only, 50-item pages. Each opening,
query and preferred-destination filter has its own cancellable request lifetime. Obsolete successes
and failures are ignored; pages cannot overlap, appended IDs are deduplicated, and a failed next page
keeps loaded choices while Retry repeats its cursor. Closing a chooser cancels its read. Selection,
known selected labels, Restore eligibility checks and save actions remain with the components.
Library filters retain their selected Location and label when canceled and reopened, including selections beyond the first page.
The shared RPC transport does not log request or response bodies. Request owners present failures;
canceling an obsolete read does not produce an application error.
Catalog search keeps its single-page Previous/Next and Location/Media semantics; mixed-resource Jobs
filters retain their own reads rather than sharing the append-only Location-choice hook.

Styling has four owners:

| Concern | Implementation |
| --- | --- |
| Application colors, type, shape and framework-wide defaults | The application theme. |
| Shared component appearance and interactive states | The owning React component, using MUI `styled`, `sx`, theme overrides and supported slots. Reuse Feedback, ActionRow, Settings shells, search popup shells and navigation instead of copying their appearance. |
| Page layout and native application-owned elements | Co-located Less/CSS; shared components keep these styles together with their markup, and no stylesheet targets another component's private DOM or state classes. |
| Measured row positions and dimensions | Dynamic styles owned by the virtual list or resizer. |

`styled` and `sx` use MUI's Emotion styling system. Less styles page layout and application-owned
HTML; it does not reskin framework components. A shared component's native markup may retain
co-located Less, while MUI controls use the theme and component APIs above.
Components own text alignment; root layout containers leave it unset.
The [entrypoint](../../frontend/src/main.tsx) configures MUI utility names before importing component
modules, including production chunks. Use exported utility classes or slots instead of hardcoded
`app-Mui*` selectors. The application theme wraps application controls, including controls placed
inside Chonky slots; Chonky owns its theme and browser appearance. Do not override all Chonky
buttons from an application stylesheet. The [application FileBrowser](../../frontend/src/components/file-browser.tsx)
owns its layout element and supplies Chonky's public theme props, so pages need no `.chonky-*`
stylesheet selectors. Component states must work under lazy route loading,
portals, narrow layouts and nested browsers without depending on import order.

`pnpm styles:check` and ESLint reject known boundary violations. Visual acceptance still checks
alignment, wrapping, focus, disabled/loading states and both browser panes; a static guard cannot
prove rendered appearance.

## Browsing and Interaction

The shared Files controller records a loaded view only after publishing its successful result. Request replacement before that point, including when Settings resolves the Library scope, remains initial loading. Superseded responses cannot settle the replacement request; each page boundary rejects obsolete work before fetching another page, and obsolete failures do not surface against the new view. A read publishes batch by batch, so a read failure has already shown part of the directory: those rows are discarded rather than presented as the directory, and a failed Library refresh falls back to the listing it last read completely. Navigation or a read failure that clears rows also clears their loaded-view identity; only successful empty responses display the empty state. A list without rows states which of the three it is - reading, empty, or failed - through one [shared placeholder](../../frontend/src/components/list-placeholder.tsx); the loading state never doubles as the empty state, and no placeholder outlives the read that owned it. Navigation publishes the target directory's breadcrumb together with the loading list, before its rows: a Location target is derived from its path, and an opened Library folder from the row or ancestor entry that opened it. A Library directory without a known entry, such as a remembered position or a located parent, keeps its breadcrumb until the response.

Every YATM file browser uses the list view through the shared application FileBrowser. Grid and view-switching actions are unavailable in menus, including selection browsers and waitlists. Browser sorting, folders-first, and Select all apply only when all rows for the current directory or query are loaded. Lists that still stream or have another page hide these actions. When sorting is available, size and date start descending, name starts ascending, and choosing the active sort reverses its direction. Media hides its hidden-file toggle because its rows have no hidden state.

[Frontend routes](../../frontend/src/app.tsx) retain Library Files/Media, Jobs All/New, and Settings. Job creation happens at `/archive`, `/restore` and `/scan`. Every horizontal tab row renders through one [page navigation](../../frontend/src/components/page-navigation.tsx) component with a documented placement - the module strip above a page, its compact secondary row, a row inside a page, or the compact Inspector row - so a row cannot take its own spacing, sizing or selected treatment on one page and a different one on another. The [Library browser](../../frontend/src/pages/file.tsx) supports compact dual-pane and Inspector modes, metadata editing, active-pane search, and locating a result in the other pane. The [Media page](../../frontend/src/pages/media.tsx) exposes Inspect, candidate-driven Volume initialization/registration, mounted state, physical browsing, and Tape/Volume Job targets. It pairs its browser with a panel the way Files pairs its own: selecting a row details the [row the list already read](../../frontend/src/components/media-inspector.tsx) beside the list - a Media by its identity, access, availability, capacity and written bytes, or one Position by its Media, path, size, both timestamps, permission and its own verification result, together with the **Archived copies** of that Position's content. Interactions inside the detail panel do not clear the selected Media or Position row. Neither needs a dialog, and a Position needs no File identity: its Preview is the content-addressed read of its Signature, and one that records none says its copies cannot be matched. **Add Volume** lists discovered disks with their registration state instead of requiring a typed path; registered, conflicting and invalid candidates stay visible but cannot be submitted, and manual entry remains available.

Files refresh only on navigation, query changes, explicit Refresh, or completion of an operation affecting that visible page. Timers, focus, visibility and Job completion do not refresh Files; hidden panes do not read. Job lists load an initial snapshot, poll revision changes and tombstones, and fetch older pages on scroll. Per-Job revisions prevent older pages from overwriting newer observations; retained tombstones prevent resurrection. Failed loads/refreshes show an error with retry, preserving cached cards. A typed NotFound response clears a deleted Job's action card. Paging stops after errors until explicit retry. Current transfer speed, historical average and server-derived stage ETA are distinct; the [shared progress contract](jobs.md) owns sampling and estimate availability. Clients render one coherent stage snapshot rather than independently estimating its remaining time.

Each visible Files panel requests one complete directory through Files.List. UI rows request the [attribute, status, operations and navigation groups](api.md#listing-projection), without per-row Get/Inspect, Preview prefetch or delayed status enrichment. Location pages read actual directories once for that request; Search owns query-bound pagination. Current-original observation failures preserve metadata with unknown current state. Reads never collect, hash or create Jobs.

An explicit per-entry read error stays in the directory and its total. The shared row mapper
shows the reason using Chonky's status and secondary-detail fields and disables selection,
opening, dragging and operations for that row. Its display-only ID cannot become a file
reference. Directory choosers also retain these disabled error rows, including unknown kinds,
while usable folders and the authorized current destination remain available. A malformed
successful row without a reference remains a protocol error. The [API filename boundary](api.md#listing-projection)
owns literal UTF-8 support and unsupported-byte escaping.

The pane shows the first received batch immediately with the exact directory total. Later displayed prefixes at least double in size and are coalesced into animation frames, limiting repeated full-array copying and Chonky processing. Completion displays every received row immediately. One transport accumulator owns the rows; completed reads reuse its final array. Cancellation, replacement and failure discard pending frames. Failed navigation and Location reads clear rows and expose Retry. A failed Library refresh restores its last complete listing with a visible error and Retry.

Locate ignores metadata responses and failures superseded by navigation or a newer Locate, so an old lookup cannot replace the current directory or reveal an obsolete selection.

**Data Usage** is an icon-only toolbar action using the existing data-usage icon and a hover/focus label. It invokes [Files.Measure](../../internal/apis/files_measure.go) once for the complete directory/query scope, under the [measurement contract](api.md#measurement). Native filesystem I/O may delay cancellation until the operating system call returns.

Measurement updates visible folder sizes and a query-wide toolbar total; ordinary loaded-row size remains a separately labeled summary. Each pane owns its cancellable measurement and discards it on navigation, query/scope changes, explicit refresh or affected operations. Pagination does not start another measurement. The same button cancels running work.

Library and Location use one stable querystring input, **More filters**, then **Search**, with Clear inside the input. Additional controls live in the dialog and compose the same server grammar, not a second client parser. Layout does not change with the source. Library search spans logical organization; Location search applies to the current real directory. Name, tags, Note, type, size, time and supported content predicates share parsing and validation; unsupported predicates fail explicitly, including in empty directories. The `has:archive` predicate describes known inventory, not a fresh health check or guaranteed recovery. Physical query pages enumerate a directory once and evaluate bounded batches without admitting files; a query continues through its cursor, and a total it cannot state is shown as unknown rather than as the count loaded so far. Search clears the preceding directory total immediately; Clear restores the preceding directories of any searched panes and ignores search responses still in flight.

Authorized path browsing skips explicit policy/resource exclusions; filesystem or resource-discovery failures fail the request instead of producing a false empty page.

Retain the product logo, build-derived version, contextual Library/Location root labels, compact row height, full-width separators, inherited surfaces, and usable empty spacing. Tape drawers close independently and physical-file panel height stays stable when expanded/collapsed. Visible dot-prefixed directories remain navigable unless a backend explicitly excludes them. Shared browser interaction fixes belong in Chonky, not per-page CSS/event workarounds.

[MUI class-name initialization](../../frontend/src/mui-classnames.ts) must run before component imports in both the application entry and browser test setup. The entry dynamically loads [application bootstrap](../../frontend/src/bootstrap.tsx) after initialization, preserving that order across production shared chunks. Cached internal selectors and rendered classes must use the same prefix; otherwise default select overflow and outlined-label styles can fail. Verify long selected values and floating labels in real rendering.

The [application theme](../../frontend/src/theme.ts) owns MUI primitive appearance; `sx` and `styled` use the same Emotion engine. Shared components own repeated structure and placement, including tabs, section cards, action rows, confirmations, feedback, result rows and saved-version choices. Less owns page layout and scoped third-party adaptations; it does not restyle those shared components. Bootstrap loads the reset before importing the application and its global styles. Component styles stay scoped, so opening a lazy route cannot change another surface. Chonky retains its own Emotion styles and notifications retain their distributed CSS.

The [Locations page](../../frontend/src/pages/locations.tsx) lives in **Settings → Locations**. Its compact table leads to routed add/detail pages; **Add location**, Refresh and pagination sit in that order at the left below the list instead of competing with the page title, and unrelated Library tools are not repeated here. Details separate configuration, live files and related Jobs, with unsaved-change protection. The detail header shows the Location's name and availability; the Configuration form owns the root path along with the other values. Its bottom action row places Save changes, Scan, Cancel and Remove location together in that order. The Directory field offers **Browse directories** before registration or while editing. Its read-only chooser uses the existing authorized path service, retains exact server paths and pages directories without collecting files; Choose changes only the draft, Cancel leaves it unchanged, and Save registers or updates the Location. Failed pages retain their retry context and closed or superseded navigation discards late replies. Browsing registered contents remains the Files tab's job; the tab fills the height the page leaves it rather than a fixed pane. **Restore destination** is a recommendation, not permission. Ignore is verbatim gitignore text; matching entries disappear from the live file list and from Restore destination choices. An explicitly named destination still writes normally, and its output stays unlinked. New and imported Locations are immediately usable. Registration does not create a collection Job. Access errors and analysis results remain separate. Shared containers unify gutters and panel gaps.

Each Chonky pane has a keyboard-accessible **Library / Locations** root menu. Files' dual panes share one source: both Library or both the same Location. Either menu changes the shared source, including the hidden pane in Inspector mode; source changes discard stale rows and selections. Directory positions, search, pagination and scrolling remain independent, with each pane remembering its directory per source. Selection browsers retain their separate waitlists. Library actions change logical organization; Location cut/paste, rename/move, mkdir and delete change actual disk entries. Neither offers user-level Copy. Shared focused-pane hotkeys and drag actions enforce same-source operation boundaries. Cross Library/Location drags never imply a filesystem transfer. Unadmitted regular files support explicit annotation/admission and Archive; unknown content has no invented version or Preview. Library visibility uses [server-side saved-version scope](library.md#visibility-and-selection), independent of Location and duplicate browsing. Root composition and interaction extensions belong to Chonky, not page overlays.

Clicking the root name returns to that source's root; its separate arrow switches sources and restores remembered navigation. Media roots also remain clickable. The compact single-line navbar uses measured available width to fold intermediate ancestors into an accessible menu, retaining root and current directory without wrapping height. Copy path writes a source-qualified display path, not an executable object reference. **Include unbacked files in Library** belongs to **Settings → Library**, separately from import/export; it is not a Files toolbar control. Settings separates its surfaces the same way the preference groups are stored: **Library** holds visibility and Trash confirmation, **Preview** holds Generation, Runtime, Output and reported formats, and **Jobs** holds the pipeline limits an attempt runs with. Each editor loads one complete typed group, keeps a local draft, and replaces that group on Save; Cancel restores the last loaded value. Save/Cancel is one page-level action row below the editable sections, never an action embedded in one section. A page states what its values apply to. All four surfaces render through one [Settings page shell](../../frontend/src/components/settings-page.tsx), one [page heading](../../frontend/src/components/page-heading.tsx), uniform section cards, one shared action row and one [field](../../frontend/src/components/settings-field.tsx) that carries a control's label, control and explanation. The framework's own components own the frame, widths and spacing, so a title, group or explanation cannot take a different size or place on one surface than on another.

Actions for one page or entity belong in one left-aligned inline row after its content, ordered from the main action at the left to less central actions at the right. Editable forms place Save first in that row and Cancel to its right; related actions, including Scan, import, export and removal, share the same row. List-level actions sit below their list; dialogs keep their actions in the footer. Navigation tabs, status indicators, field controls and contextual browser tools stay with the content they control. The [shared action row](../../frontend/src/components/action-row.tsx) owns alignment, spacing and horizontal scrolling on narrow screens, keeping actions together without shrinking their buttons. Settings pages and their forms use the available content width without a separate narrow maximum. Settings groups use one restrained card treatment: a clear section heading, a separated body with consistent field spacing, and explanations next to the setting they describe. Location's Advanced settings use the same section component and are initially collapsed in one bordered section; expanding it reveals default-off mmap content reads without a nested card.

Double-clicking a file in ordinary Library/Location and Archive/Restore source browsing opens details, never a content tab or an implicit waitlist addition. Location entries with a File association use the same Library details and saved versions; unadmitted entries show live properties without forcing admission. Double-clicking a directory navigates into it. Original details link to the live containing folder and reveal the file; they do not add a separate Open button. Archived copies show health and availability with Restore guidance, not an HTTP content link. A dedicated file picker may use double-click to choose its entry; Library search retains its locate-result behavior.

Library, Jobs and Preview Settings share the same loading, retry and save feedback. Location removal uses the shared confirmation dialog, retaining an error in that dialog for correction and retry.

Composed browsers connect pagination to `FileList.onScroll`; `FileBrowser` is the state container and does not forward that event to an explicitly supplied child. Integration tests render the installed list component as well as testing the paging hook, so a mocked wrapper cannot conceal a disconnected native scroll handler.

The [shared query bar](../../frontend/src/components/library-filters.tsx) keeps optional structured controls out of the workspace. Find identical files opens **Tools → Identical files**. Ordinary queries, including `has:duplicates`, remain flat file results. Duplicate semantics belong to [Library search](library.md#annotation-search-and-cleanup). Inspector is the default unless Dual pane was saved; both keep the complete Chonky toolbar and dot-directory navigation.

Rows use the [Library state matrix](library.md#file-and-version-display-states): present/archive green, present/no-archive yellow, absent/archive blue, absent/no-archive red and uncertainty gray. Current changes and historical anomalies use a supplementary mark, never an implicit health expiry. Files.List computes requested status using batched existence facts and bounded current-original observations, without hashing or reading Media. No exact copy counts, versions or signature bytes accompany ordinary list rows.

The [controlled detail flow](../../frontend/src/pages/file-detail.tsx) is keyed by a `FileOperationRef` and uses `FilesService.Get` for both Library and live Location entries. The [shared detail surface](../../frontend/src/components/detail-surface.tsx) owns the same compact header, optional status, fixed tab row, Preview region, and scroll boundary in the Files Inspector, Files dialog, and Media/Position Inspector; each caller supplies its own facts and operations. The Files dialog uses the same content as the Inspector and becomes full-screen on small viewports. Basic detail loading does not wait for Preview or history; versions load on first opening Saved versions, and that version's copies load with its detail. Each region owns errors, retry and stale-response rejection. A refresh retains the last coherent snapshot with one unobtrusive indicator; late responses for another entry cannot clear or replace the current selection. Selecting another entry clears the previous snapshot and holds its layout as a skeleton until the new detail arrives, while retaining the selected Overview or Saved versions tab. The [File content](../../frontend/src/components/file-content.tsx) keeps a fixed Overview/Saved versions tab row while Preview stays above the selected tab's content. The image or video display area is a responsive 16:9 frame; video controls sit below it, and media fit without stretching. Overview keeps the original, inline Tags/Note editing with Save/Cancel, and collapsed technical details together. Overview shows **Add to Archive list** only when the entry publishes the Archive operation and a regular Library File has an original association. Directories offer their root without checking descendant original associations. Saved versions use a paginated dated list with the newest loaded archive time first. File details and the Restore picker use one [saved-version choice](../../frontend/src/components/saved-version-choice.tsx) for selected, disabled and keyboard-focus presentation; each caller retains its own content and selection. A version shows its recorded last archive date, then its first archive date; without either it reads **Date not recorded**. Matching copy write dates do not establish when that FileVersion was archived. **Add to Archive list** and **Add to Restore list** lead the bottom action rows of Overview and the selected saved version, respectively. The selected saved version can be added to the Restore waitlist by its exact `FileVersion` identity. Both additions retain the Inspector or dialog, report whether the item was added or already present, and expose **View list**; neither chooses Media or a destination, estimates a Job, or creates one. Copies are immediately visible as individually collapsible MUI cards with a right-side icon arrow; signature, hash and permissions stay in collapsed technical details. A current original's Preview is never replaced by saved assets. An entry with no current original previews its newest saved version instead, under a label naming that version, and shows no Preview when it has no saved version either. Archive-only Files use the same eligible-history summary as the list. Saved content remains available through [Library publication](library.md#archive-inventory); Restore execution remains the explicit waitlist review and Job creation workflow. Duplicate queries never merge organization. Originals are not archive copies.

Persistent copy is limited to names, paths, facts and actions. Location names are user-defined directory labels, not product modes. Overview labels the association **Location** and shows its name and physical relative path as inline links separated by a slash. The name opens the live Location root; the path opens its containing folder and reveals the file, including later pages. An original hidden by user Ignore opens that folder without appearing in it, because explicit access does not make the entry browsable. It has no redundant location heading or missing-location paragraph. Archive-only entries use the neutral **Saved versions only** label. Location pages and Scan dialogs omit generic introductions and repeated operation descriptions. The selected File header does not repeat the domain model; version lists do not repeat archive rules, and copy lists do not repeat their section context. Empty/unavailable/error states retain concise next steps. The selected version's Preview uses that version's endpoint; switching versions clears the previous image, including when a prior response arrives late. Successful File refreshes update original facts, loaded version/copy pages and selected-version Preview while retaining the tab and selection. A current Preview is read under the content signature the detail published, which the Library only publishes while the live original still agrees with its record. Path review, Ignore semantics, destructive-action scope and Restore destination/non-in-place warnings remain at their relevant operations.

**Jobs → New → Scan** orders its controls as source, target, signature policy, result handling and Preview. Location and Media use required single-choice, server-search fields with bounded ID-cursor pages; free text is not a selection. Search matches registered names and directory paths or Media identities, treating wildcard characters literally. Loading, empty results and retry stay in the chooser. Stale responses cannot overwrite a newer search or selection. Inventory update and recorded-copy verification are mutually exclusive policies. Verification forces real reads; sequential Media disallow Preview. The shared Preview select offers **Don’t generate / Generate missing / Regenerate all** in Scan and Archive. [Preview](preview.md) owns execution semantics. All modes use the same SCAN runner and result types.

The browser remembers successfully submitted Scan choices in local storage. Returning reloads the selected target and checks eligibility/binding before enabling submission; incoming source/selection links take precedence. Invalid storage or unavailable targets cannot silently select another resource. Signature, result and Preview constraints still apply to remembered choices.

Ordinary Library and Location edits share [one controller](../../frontend/src/components/file-operations.tsx), Chonky action handling, name dialogs and `FilesService.Mkdir/Move/Remove`. Typed references select logical File IDs or live Location entries; mixed-scope requests are rejected before mutation. Copy is unsupported and must not silently become a move. Scope-specific primitives and deletion safety follow the [shared organization contract](library.md#shared-organization-interface).

Edits do not create Jobs or insert workspace progress rows. Short operations remain silent; requests exceeding 500 ms show a fixed notification. Rename displays **Renaming…** without Cancel because its admitted filesystem change and Library update finish together. Other file operations expose cancellation between their individual changes. Name/confirmation dialogs await execution, prevent repeated submission and retain failures. Completion, partial failure or cancellation refreshes affected panes. Refresh failure after successful mutation is reported separately, without keeping a retryable mutation dialog open. Leaving Files aborts pending requests; already admitted physical changes still settle. Bounded item results and the final summary distinguish settlement from complete success.

**Archive** has one creation flow: Library/Location browsing plus a Chonky cross-directory selection list. Restore uses the same accumulation model. Files exposes symmetric **Add to Archive list** and **Add to Restore list** actions for its current multiselection. These actions update the same browser-session waitlists used by `/archive` and `/restore`, retain the current Files pane and selection, and provide **View list**; they never create a Job. Archive accepts only rows whose current observation publishes the Archive operation. Restore regular-file rows use an automatic saved-content selection, while directories retain their bounded root selection. Dragging into the list only adds selections. Directory rows remain roots; expansion and deduplication are bounded on the server. Selection edits automatically request estimated counts/bytes, separately exposing unknown sizes, unavailable inputs and ignored outputs; superseded responses are discarded. Missing signature does not mean missing size. The waitlist footer contains only **Archive…** or **Restore…**, opening an application dialog with options, estimates, warnings and final preparation. Opening or cancelling it creates no Job and preserves the selection and options. Preparation performs authoritative checks; known missing originals/copies block it. Full paths remain in selection rows and Restore destination controls. Logical bytes do not predict compressed Tape capacity.

Restore keeps automatic File/directory selections distinct from explicit FileVersions. Adding a saved version from File details stores that exact `FileVersion.id`; a Position or archived-copy record is never treated as a version. An explicit version replaces that File's automatic row, and a later automatic addition cannot overwrite it; repeated additions are deduplicated, while different explicit versions of the same File may coexist. The creation dialog chooses latest saved content or the latest recorded archive date at or before a local date/time. Automatic rows follow that policy; custom versions remain fixed. **Change version** or double-click opens a paged version picker with the selected content's Preview and copy availability. **Apply current policy to all** resets custom choices. Unmatched selections stay visible and block preparation until removed, changed or explicitly skipped for that cutoff; missing copies are a separate blocker and are never covered by the skip. Changing selections or the time policy invalidates skip consent. Waitlist selections and policy survive navigation within the browser session. The server owns [historical resolution](library.md#organization-and-content), directory expansion and frozen Job choices; this is not a historical directory snapshot.

Archive and Restore waitlist directories open inside the same pane, with parent/root breadcrumbs and complete immediate children through Files.List. Browsing does not replace the selected roots, collect files, or execute filesystem actions. Removal applies to explicit rows at the waitlist root, not implicit descendants. Nested Restore files use the same version picker; custom choices are submitted alongside the directory root and replace that File's automatic version. The visible rows resolve automatic versions against the global time policy; failed or superseded reads cannot restore stale child rows.

Generic workflow explanations belong in documentation, not persistent Job cards, Scan forms or Media read dialogs. Progress, results, required Media and recovery actions remain visible. Metadata editing and matching-file views use labels and data without repeating what tags, notes or independent Files mean; bulk-edit scope and safety warnings remain explicit. Tag inputs search the server after a short debounce and page matching suggestions through the server cursor without loading the complete Tag set into the browser or imposing a fixed total-suggestion cap. Search text alone is not an edit: a Tag enters the draft only when selected, including the explicit add-new suggestion, or added with Enter.

When an original's content signature becomes unknown, its Preview clears the preceding error and offers no retry for that unknown content.

All Scan entry points open the same [controlled form](../../frontend/src/components/scan-form.tsx) at `/scan`: source/range, Signatures, Results, Find matching Library content, Previews, then **Start scan**. Location and Media use required server-search selectors. Location supports the whole root or selected entries within that Location; Files supports Library/Location roots accumulated across directories; Media remains whole-resource. The read-only Chonky range dialog edits a temporary selection: Choose commits it, Cancel discards it. ## Identical Files

[The tool](../../frontend/src/pages/identical.tsx) separates Library connected histories from scoped Location originals. One continuous sparse Chonky list spans all groups with a global scrollbar; unloaded positions show placeholders and visible pages load automatically. Group headers are not file identities. Group selection and actions remain scoped, and the right Inspector follows the last operated member while actions consume the full selection.

Selected members remain pinned while pages are replaced, including selection changes made during a pending sort or hidden-file lookup. Page replacement and selected-row position updates happen together, so the virtual list never receives the same member at both its old and new positions. Chonky's selection-change event owns that selection; click/open snapshots describe the action's earlier state and only choose the Inspector member.

Opening the tool queries nothing: an explicit **Find** starts a global search and repeats it on demand, and a source or scope change clears results and selection. The Locations source has a searchable multi-select whose chips are the selected whole Locations. The retained result supplies bounded rows for arbitrary scroll positions; missing pages retry without discarding loaded pages. The hidden-file toggle switches between two positions computed by the same Find. The list uses fixed group-title order; **Sort by name** and **Sort by size** reorder complete groups' members through the retained result without another Find. Name starts ascending and size starts descending; clicking the active sort reverses its direction. Delete, Keep and Merge wait while a sort remaps row positions; sorting also waits for active file operations. Date sorting, view switching, folders-first and Select all are unavailable on this sparse list. A result lost through expiration or restart asks for another Find rather than silently searching again. Version removal remains available through the shared Saved versions detail.

Independent Remove requests may overlap, including different files in one Location. The action is labeled **Delete**, as in ordinary file lists; its confirmation explains that the selected files move to Trash. Identical Delete and Keep confirmations close after admission; per-file progress and failure remain in the list, allowing another file to be deleted while the first request is pending. A physically removed row disappears when its result arrives; a publication-pending row also disappears with an explicit Library warning. Failed and unprocessed rows retain diagnostics. Changed groups show their remaining file count but are not regrouped until Find; Keep and Merge are unavailable on them. A successful Merge removes its group; partial Keep updates the affected members, including members that were not loaded. Neither these actions nor Inspector or metadata updates automatically start a new Find. [Library](library.md#identical-file-tools) owns matching, merge, Trash and historical Job semantics.
