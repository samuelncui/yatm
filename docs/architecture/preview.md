# Preview Storage

Preview is an optional stage of the unified [Scan pipeline](jobs.md#scan), not a separate runner or Job kind. It accepts random-readable Location/Library selections and supported mounted Media from the Scan manifest under the same signature policy. Sequential Tape sources reject Preview rather than staging or implicitly restoring content. Report-only scans do not admit Files merely to generate derivatives.

Generation is off by default. The shared Preview policy selects none, missing-only or regenerate-all. KNOWN_ONLY without a usable content identity skips and counts the entry, without hashing. FILL_MISSING and FORCE_READ acquire required facts through ACP. Generators may read source bytes but cannot upgrade the hash policy. Generator failures are per-item findings, not a rollback of valid observation publication.

Archive can create a companion SCAN configured for Preview after successful indexing, from its already frozen manifest. It does not independently re-admit or rescan live roots. Archive progress retains the companion Job ID or creation error. Companion failure does not undo Archive preparation or copying; there is no cross-Job transaction or compensation.

## Generation

The Scan manifest retains content facts and the entries whose Preview failed, with the reason. Whether content already has assets is the [content-addressed store's](../../internal/preview/preview.go) answer: a bundle is renamed into place, so one `stat` decides reuse and no manifest is opened to ask. Nothing records a successful outcome per entry - a row's reported outcome is derived when results are read, from its recorded failure, the bundle's presence, or neither. Each attempt reads the Scan manifest under its own Job boundary. The shared content stage supplies the source path and content identity to the Preview manager; the manager invokes the generator once without before/after source checks. Source enumeration, cancellation and checkpoint behavior belong to Scan.

One attempt generates a content once and then serves every File holding those bytes from the same bundle, in every policy; missing-only asks the store first, so already published content costs no decoder call. A Job reports its Preview counts from the attempt that produced them, the way it reports its speed.

Generators are registered by kind and configured extensions. Selection and generation use the actual original filename, not its independently organized Library name. **Settings → Preview** persists a master enable switch, per-kind and per-extension switches, image dimensions, video poster/tile dimensions, sampling interval/frame count and output format/quality. Shared execution settings select the helper command, concurrent files, per-file timeout and maximum input pixels. SettingsService replaces the complete typed Preview group; Save applies without restarting. New Scan Jobs, including Archive companions, freeze output settings in their bundle; live enablement and capacity are checked before each file starts. Disabling generation allows already-running files to finish and skips later files. Existing bundles remain readable regardless of generation switches and remain unchanged until explicitly regenerated.

The installer explicitly converts legacy YAML generator options and removes that YAML block; a saved Preview group takes precedence. Startup does not import legacy generation options. [Configuration conversion](../operations/migration.md#configuration-review) owns the upgrade sequence. Library export/import never carries Settings. Only `preview.root`, the deployment-owned asset-store path, remains in YAML. CLI reads preferences with `settings preview` and replaces them with `settings preview --preview-json <file>`; the file contains the `PreviewSettings` protobuf JSON shape.

Output dimensions, sampling, assets, manifest, and output bytes are bounded. Video defaults use 320×180 timeline tiles, a 10-second sampling interval and at most 30 frames. Video timeline tiles retain their configured dimensions, including odd sizes, so encoded sprites and WebVTT coordinates agree regardless of the source pixel format. The native timeline slider occupies the full height of its controls row for pointer interaction. Pointer positions select the nearest sampled time; arrow keys move between actual sampled frames, including irregularly spaced frames.

The settings editor uses a searchable Type selector and one card at a time, without repeating the selected type as a card heading. Image/video types use descriptive names; multiple routes of the same type are distinguished by extensions. File extensions use a searchable multi-select: selection enables a route, deselection retains it disabled, and custom extensions remain editable. Per-kind helper capabilities supply suggestions; unconfirmed extensions stay visible rather than being discarded. Switching cards preserves unsaved edits, and Save returns to any card with invalid parameters. The Supported formats section shows helper capabilities and dependency versions before Save and Cancel; failed or pending rechecks retain the prior information and draft. The master switch defaults off; configured kinds and extensions default on beneath it. Disabling a kind or extension retains its parameters. The helper path, input pixel limit and timeout are read after a file acquires an execution slot; changes do not alter the Job's frozen output dimensions, format or quality. `PreviewService.GetCapabilities` and `yatm-cli preview capabilities` probe the installed helper separately from enablement and asset reads. Explicit Scan or Archive generation requests fail before Job creation when the master switch is off or the helper is unavailable. A later failure creating Archive's companion does not invalidate the prepared Archive.

Unchecking an extension retains its disabled route. Deleting its selected chip removes that route, allowing corrections or reassignment to another configured generator without discarding the other draft settings.

### Native Helper

The main service remains independent of FFmpeg. The optional `yatm-preview` executable owns native decoding and encoding in a separate process, using the bounded JSON Lines protocol in [previewprotocol](../../internal/previewprotocol/protocol.go). Each invocation handles one source and writes role-labelled assets into a caller-owned temporary directory. Progress reports distinguish opening, seeking/decoding, encoding and publication. The manager validates output roles, paths, sizes and dimensions before publishing the bundle. Cancellation terminates the process and removes unfinished outputs.

The command defaults to a helper beside the main executable, then `PATH`; it never substitutes a system FFmpeg command. The [build contract](../../previewworker/build/README.md) owns native dependency versions, supported package targets, private-library layout and source distribution. Missing native dependencies disable generation, not the main service, browsing or existing assets. Old Alpha generator command fields are rejected before catalog writes; the supported legacy configuration conversion remains the v0.1.x migration path.

Relative source paths and `paths.work` resolve from the service working directory. An absolute `preview.root` is used directly; a relative root resolves under `paths.work`, with `previews` as the default. The shared caller passes absolute source and output paths to the helper; generation does not rewrite deployment configuration.

Image generation uses LibRaw for DNG, CR2, CR3, NEF, NRW, ARW, RAF, ORF, RW2, PEF and SRW. It selects the smallest embedded preview large enough for the requested output, falling back to actual RAW development when previews are absent, damaged or undersized. Development uses camera white balance with LibRaw's missing-metadata fallback, sRGB output and half-size decoding when sufficient. Orientation is applied once before final resizing. These extensions are routing capabilities, not a guarantee that every camera or compression variant is supported. The installed helper reports its LibRaw version and per-kind input formats; RAW shares Image output settings and the existing asset contract.

### Resource Limits

One manager bounds active files across all Jobs (default two, configurable 1–16), shares in-flight generation for identical content and admits at most 64 distinct pending content keys. Queue saturation is an explicit item failure. The per-file timeout defaults to 600 seconds and starts after acquiring a slot, not while waiting. Each decoder uses two slice threads. Input dimensions are checked before decoding against the configured limit (default and maximum 64 million pixels). Native allocation requests, bytes read per seek, packets inspected, output dimensions, asset count and bundle bytes are bounded independently. These limits are not a fixed process-RSS ceiling: a 100-million-pixel sprite alone needs roughly 400 MB of RGBA storage, in addition to decoder and encoder buffers. Capacity acceptance must measure the media and concurrent workload; service cgroup memory can include filesystem cache, not just process RSS.

RAW uses LibRaw's decoder-allocation guard, scaled with the configured input-pixel limit and capped at 512 MiB, and rejects processed buffers over 256 MiB. The decoder guard does not include all development, resize and encoder allocations. Large developed outputs can therefore exceed 512 MiB of process RSS; concurrency and output dimensions remain separate resource controls.

Video timelines open the input and decoder once, issue ascending sparse backward seeks and decode keyframes only. The poster and timeline share sampled frames. Repeated keyframes are deduplicated; WebVTT carries actual normalized presentation timestamps rather than claiming an exact frame at each requested time. Sampling does not fall back to sequential decoding or per-frame subprocesses. The worker bounds demux reads to 64 MiB for opening and each seek and inspects at most 4,096 packets per sample. Containers lacking sufficient header metadata, unsupported codecs, unavailable keyframes and corrupt frames produce explicit failures instead of an unbounded probe. Temporary frames remain in bounded memory rather than per-frame files; publication failure or cancellation removes temporary output assets.

## Addressing and Update Policy

The current producer uses the Library v1 signature from SHA-256 plus size. The [manager's bundle path](../../internal/preview/preview.go) shards its hexadecimal form into three successive two-character directories and names the indexed ZIP with the remaining characters. [Bundle storage](../../internal/preview/storage.go) puts `manifest.pb` and generated assets inside that ZIP. Direct role-based asset reads do not require unpacking the full bundle or a Preview database.

Missing-only generates assets for known content without an existing bundle. Regenerate-all replaces existing bundles even when generator settings are unchanged, independently of the signature policy; it also permits replacing damaged derivatives. Identical content shares assets across independently organized Files and versions and is generated once per Scan. Archive's companion Scan uses the same policy. Job deletion does not remove bundles.

[PreviewService.Get](../../entity/preview.proto) reads metadata independently of Files.Get/List and version pagination. Its request is the content signature itself, because Preview storage is content-addressed: a caller resolves a File, a saved version or a recorded Position to that signature before asking, and content the Library cannot name is never requested. Results distinguish READY from NOT_GENERATED. Storage errors stay within the Preview region. Server-generated [resource URLs](../../internal/apis/preview_service.go) bind the content identity and the manifest-owned role; asset requests revalidate that binding. A current original's Preview is read only under the identity its own observation published - `FilesDetail.content_signature`, present while that observation applies - so unknown or changed current originals never borrow saved-version assets. Reads neither admit, hash, observe nor generate content. [Generator tests](../../internal/preview/generator_test.go) and [Preview E2E](../operations/e2e-test.md#preview-update-policy) cover generation separately.

## Asset State

Asset validity is derived independently from the [Job lifecycle](jobs.md). It does not add catalog Job states.

| Observation | Display and allowed operation | Failure/retry |
| --- | --- | --- |
| Current content unknown | No current Preview; explicit saved versions remain selectable | Request a Scan that acquires missing facts |
| Matching readable bundle | Serve the requested role | Job removal does not remove assets |
| Bundle absent or damaged | Keep File/version metadata; report missing/error on asset access | An explicit Scan with Preview can regenerate |
| Generator settings outdated | Keep the asset in missing-only mode | Regenerate-all replaces it |
| Generation fails or is canceled | Keep completed assets and successful Scan observations | Create a new Scan for another generation attempt |
