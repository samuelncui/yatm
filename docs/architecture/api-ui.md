# APIs and User Interface

## Public Interfaces

[Protobuf sources](../../entity) are authoritative; Go and TypeScript outputs are generated. The public control API remains gRPC. The shared typed router handles protobuf oneof-to-oneof dispatch; conversion, validation, migration, and external events can use direct type switches.

| Service | Responsibility |
| --- | --- |
| [Library Service](../../entity/service.proto) | Scoped/paginated Files, annotations/search, Tags, Media/Positions, Volume initialize/register, devices, Library Trim |
| [JobService](../../entity/job.proto) | Common catalog, delete/cancel, retry indexing, logs |
| [ArchiveJobService](../../entity/job_archive.proto) | Create, WriteMedia, progress, manifest pages |
| [RestoreJobService](../../entity/job_restore.proto) | Create, RestoreMedia, progress, Media/candidate pages |
| [FilesService](../../entity/files.proto) | Pure provider-neutral List/Get, observed state, explicit collection and annotation |
| [ScanJobService](../../entity/job_scan.proto) | Configurable source/content/result policies, ReadMedia, progress and paged entries/scopes |
| [LocationService](../../entity/location.proto) | Register/list/get/update/confirm/delete, live directory/entry reads and explicit admission |
| [FileCatalogService](../../entity/location.proto) | Original/coverage, FileVersions, copies/duplicates, selection inspection, inventory admission and manual original relocation |
| [SettingsService](../../entity/settings.proto) | Independent collection/visibility/delete-confirmation preferences, access summary and authorized path browsing |
| [FileOperationService](../../entity/file_operation.proto) | Shared Library/Location organization, streaming per-item results and final summary; no Job |

Archive/Restore use typed Tape/Volume operation targets. A kind's service is registered with its runner; Job listings include kind and optional target identity/name for routing and filtered history. New input browsing reads actual Location directories or authorized Settings paths. [Source selections](../../entity/source.proto) remain only as frozen legacy Job data, not public raw-directory RPCs.

[HTTP transfer endpoints](../../apis/files.go) serve Library export/import, Preview roles, and GET/HEAD `/content/:position_id`. Direct content reads require a mounted concurrent-random-readable Volume and revalidate marker, profile, safe path, mode, size, and mtime; stale file facts return a conflict requiring Scan. Range is supported without a Restore Job. There is no file or Preview Download action/CLI command or force-download query option. Open and Preview retain their content endpoints; unsafe content still uses attachment disposition rather than becoming an active same-origin page. Library metadata Export is independent and remains available. Loopback-only upgrade endpoints report running operations and quiesce admission for preflight.

[Original content](../../apis/online_content.go) has its own GET/HEAD `/originals/:file_id` endpoint, bound to location_id and publication revision; stale links cannot silently read a rebound observation. Each request checks local confirmation, the individual observation's binding token, administrator boundary, symlink components, and recorded file facts, then serves Range/content from the same opened descriptor. No Location-wide analysis is required. Known changes return conflict. Active formats use attachment disposition with `nosniff` and sandbox policy. No Restore Job or extra full-file hash is performed; trusted relatively stable sources, not concurrent hostile path replacement or snapshot-consistent reads, define the safety boundary.

Files.Get supplies a guarded `content_reference` immediately before Open. GET/HEAD `/files/content?ref=...` accepts its base64url protobuf-JSON FileOperationRef, never a bare File ID reinterpreted as new bytes. The underlying observed reference binds the provider, root and object facts. The same descriptor, Range and safe disposition rules apply without an admitted File or signature. User Ignore does not prevent explicit regular-file access. Physical mutations accept typed relative references, never shell commands or unrestricted absolute paths.

## Browsing and Interaction

[Frontend routes](../../frontend/src/app.tsx) retain Library Files/Media, Jobs All/New, and Settings. The [Library browser](../../frontend/src/pages/file.tsx) supports compact dual-pane and Inspector modes, metadata editing, active-pane search, and locating a result in the other pane. The [Media page](../../frontend/src/pages/media.tsx) exposes Inspect, Volume initialization/registration, mounted state, physical browsing, and Tape/Volume Job targets.

Live filesystem and Library browsers use ordinary polling, not a general change log or per-file event stream. Job lists load an initial snapshot, poll revision changes and tombstones, and fetch older pages on scroll. Per-Job revisions prevent older pages from overwriting newer observations; retained tombstones prevent resurrection. Failed loads/refreshes show an error with retry, preserving cached cards. A typed NotFound response clears a deleted Job's action card. Paging stops after errors until explicit retry. Current transfer speed is separate from historical-average ETA, and information tooltips explain estimates.

Library directory/search refreshes reload the loaded page window through bounded requests and replace it only when the whole refresh succeeds. Location pages read the actual current directory with query filtering before pagination and cursors bound to directory facts/root/query. Pure Files reads never admit, even for linked originals; ordinary Files browsing may explicitly request automatic collection afterward, while directory pickers do not. Failed Location reads clear rows and expose Retry without offline fallback. Entries carry observed references and optional real File associations. Collection failures are separate and cannot fabricate IDs. There is no watcher or periodic recursive scan.

Library and Location use one stable querystring input, **More filters**, then **Search**, with Clear inside the input. Additional controls live in the dialog and compose the same server grammar, not a second client parser. Layout does not change with the source. Library search spans logical organization; Location search applies to the current real directory. Name, tags, Note, type, size, time and supported content predicates share parsing and validation; unsupported predicates fail explicitly, including in empty directories. The `has:archive` predicate describes known inventory, not a fresh health check or guaranteed recovery. Physical query pages enumerate a directory once and evaluate bounded batches without admitting files.

Only File ID zero denotes the virtual Library root. The reserved Trash ID -1 is looked up as a persisted directory; missing IDs return NotFound, not an empty directory. CLI read commands accept it as `file get/list/parents -- -1`, without relaxing mutation validation. Authorized path browsing skips explicit policy/resource exclusions; filesystem or resource-discovery failures fail the request instead of producing a false empty page.

Retain the product logo, build-derived version, contextual Library/Data Source root labels, compact row height, full-width separators, inherited surfaces, and usable empty spacing. Tape drawers close independently and physical-file panel height stays stable when expanded/collapsed. Visible dot-prefixed directories remain navigable unless a backend explicitly excludes them. Shared browser interaction fixes belong in Chonky, not per-page CSS/event workarounds.

[MUI class-name initialization](../../frontend/src/mui-classnames.ts) must run before component imports in both the application entry and test setup. The entry dynamically loads [application bootstrap](../../frontend/src/bootstrap.tsx) after initialization, preserving that order across production shared chunks. Cached internal selectors and rendered classes must use the same prefix; otherwise default select overflow and outlined-label styles can fail. Verify long selected values and floating labels in real rendering.

The [Locations page](../../frontend/src/pages/online.tsx) lives in **Settings → Locations**. Fixed navigation links compact tables to routed add/detail pages with inline Save/Cancel and unsaved-change protection. Details separate configuration, live files and related Jobs. **Restore destination** is a recommendation, not permission. Ignore is verbatim gitignore text. New Locations are immediately usable; imported paths require review. Registration discloses initial basic collection when enabled. Access errors, confirmation and analysis results remain separate. Shared containers unify gutters and panel gaps.

Each Chonky pane has a keyboard-accessible **Library / Locations** root menu. Files' dual panes share one source: both Library or both the same Location. Either menu changes the shared source, including the hidden pane in Inspector mode; source changes discard stale rows and selections. Directory positions, search, pagination and scrolling remain independent, with each pane remembering its directory per source. Selection browsers retain their separate waitlists. Library actions change logical organization; Location cut/paste, rename/move, mkdir and delete change actual disk entries. Neither offers user-level Copy. Shared focused-pane hotkeys and drag actions enforce same-source operation boundaries. Cross Library/Location drags never imply a filesystem transfer. Unadmitted regular files support explicit annotation/admission and Backup; unknown content has no invented version or Preview. Library visibility uses [server-side saved-version scope](library.md#visibility-and-selection), independent of Location and duplicate browsing. Root composition and interaction extensions belong to Chonky, not page overlays.

Clicking the root name returns to that source's root; its separate arrow switches sources and restores remembered navigation. Media roots also remain clickable. The compact single-line navbar uses measured available width to fold intermediate ancestors into an accessible menu, retaining root and current directory without wrapping height. Copy path writes a source-qualified display path, not an executable object reference. **Include unbacked files in Library** belongs to **Settings → Library**, separately from import/export; it is not a Files toolbar control.

Double-clicking a file in ordinary Library/Location browsing opens details, never a content tab. Location entries with a File association use the same Library details and saved versions; unadmitted entries show live properties without forcing admission. Double-clicking a directory navigates into it. Original details link to the live containing folder and reveal the file; they do not add a separate Open button. Archived-copy content retains its explicit Open action. A dedicated file picker may use double-click to choose its entry; Library search retains its locate-result behavior.

Composed browsers connect pagination to `FileList.onScroll`; `FileBrowser` is the state container and does not forward that event to an explicitly supplied child. Integration tests render the installed list component as well as testing the paging hook, so a mocked wrapper cannot conceal a disconnected native scroll handler.

The [shared query bar](../../frontend/src/components/library-filters.tsx) keeps optional structured controls out of the workspace. Grouped duplicate presentation is an explicit view choice rather than a substring inference from arbitrary query text. Duplicate semantics belong to [Library search](library.md#annotation-search-and-cleanup). Inspector is the default unless Dual pane was saved; both keep the complete Chonky toolbar and dot-directory navigation.

**Duplicates in Locations** opens [grouped results](../../frontend/src/components/duplicate-groups.tsx), not a client-side grouping of one FileSearch page. Collapsed headers show a representative filename, complete file/Location counts, archived-copy count and size when consistent. One expanded group uses Chonky's shared `GroupedFileList`, ordinary file actions and Inspector; list rows show both logical and physical paths. Group and member pagination/loading/retry are independent. Signature bytes stay in a secondary disclosure with Copy. Filters select whole groups and mark outside-filter members. Polling preserves an unchanged expansion; observed index or summary changes clear loaded members and offer Refresh. Late responses cannot restore a previously closed group.

Rows use the [Library state matrix](library.md#file-and-version-display-states): present/backup green, present/no-backup yellow, absent/backup blue, absent/no-backup red and uncertainty gray. Current changes and historical anomalies use a supplementary mark, never an implicit health expiry. Files.Inspect checks visible originals in bounded requests without hashing or reading Media. Tooltips remain short, keyboard-accessible and left-opening. Directories show no fabricated aggregate state but reserve the same column width. The [source-built Chonky patch](../../frontend/patches/README.md) owns aligned columns and measured rows, not page overlays.

The [content Inspector](../../frontend/src/components/file-content.tsx) keeps status to one short line with a tooltip and relevant actions, followed by **Overview** and **Saved versions**. Overview keeps the original, tags and Note together; saved content uses a paginated dated list. Missing dates read **Archive date not recorded**, without an additional explanatory paragraph or substituting import time or file modification time. A known last-backup date remains visible independently. Copies show storage names; signature/hash/permissions are secondary details. Unknown originals never borrow a historical Preview. Archive-only Files use the same eligible-history summary as the list. Covered originals show the durable version established by [Library publication](library.md#archive-inventory), with its copies and Restore action; another backup is not required to create that version. Duplicate queries never merge organization. Online originals are not backup copies.

Persistent copy is limited to names, paths, facts and actions. Location names are user-defined directory labels, not product modes. Overview shows a compact Location chip and clickable physical relative path inline. The chip opens the live Location root; the path opens its containing folder and reveals the file, including later pages. It has no redundant location heading or missing-location paragraph. Archive-only entries use the neutral **Saved versions only** label. Location pages and Scan dialogs omit generic introductions and repeated operation descriptions. The selected File header does not repeat the domain model; version lists do not repeat backup rules, and copy lists do not repeat their section context. Empty/unavailable/error states retain concise next steps. The selected version's Preview appears before its restore action and uses that version's endpoint; switching versions clears the previous image, including when a prior response arrives late. Successful File refreshes update original facts, loaded version/copy pages and selected-version Preview while retaining the tab and selection. Current Preview validity compares hash/size, not opaque signature bytes. Path review, Ignore semantics, destructive-action scope and Restore destination/non-in-place warnings remain at their relevant operations.

**Jobs → New → Scan** orders its controls as source, target, signature policy, result handling and Preview. Location and Media use required single-choice, server-search fields with bounded ID-cursor pages; free text is not a selection. Search matches registered names and directory paths or Media identities, treating wildcard characters literally. Loading, empty results and retry stay in the chooser. Stale responses cannot overwrite a newer search or selection. Inventory update and recorded-copy verification are mutually exclusive policies. Verification forces real reads; sequential Media disallow Preview. The shared Preview select offers **Don’t generate / Generate missing / Regenerate all** in Scan and Backup. [Preview](preview.md) owns execution semantics. All modes use the same SCAN runner and result types. Imported paths require local confirmation.

The browser remembers successfully submitted Scan choices in local storage. Returning reloads the selected target and checks eligibility/binding before enabling submission; incoming source/selection links take precedence. Invalid storage or unavailable targets cannot silently select another resource. Signature, result and Preview constraints still apply to remembered choices.

Ordinary Library and Location edits share [one controller](../../frontend/src/components/file-operations.tsx), Chonky action handling, name dialogs and `FileOperationService.Execute`. Typed references select logical File IDs or live Location entries; mixed-scope requests are rejected before mutation. Copy is unsupported and must not silently become a move. Scope-specific primitives and deletion safety follow the [shared organization contract](library.md#shared-organization-interface).

Edits do not create Jobs or insert workspace progress rows. Short operations remain silent; requests exceeding 500 ms expose Cancel in a fixed notification. Name/confirmation dialogs await execution, prevent repeated submission and retain failures. Completion, partial failure or cancellation refreshes affected panes. Refresh failure after successful mutation is reported separately, without keeping a retryable mutation dialog open. Leaving Files aborts pending work. Bounded item results and the final summary distinguish settlement from complete success.

**Backup** has one creation flow: Library/Location browsing plus a Chonky cross-directory selection list. Restore uses the same accumulation model. Dragging into the list only adds selections. Directory rows remain roots; expansion and deduplication are bounded on the server. Selection edits automatically request estimated counts/bytes, separately exposing unknown sizes, unavailable inputs and ignored outputs; superseded responses are discarded. Missing signature does not mean missing size. The waitlist footer contains only **Backup…** or **Restore…**, opening an application dialog with options, estimates, warnings and final preparation. Opening or cancelling it creates no Job and preserves the selection and options. Preparation performs authoritative checks; known missing originals/copies block it. Full paths remain in selection rows and Restore destination controls. Logical bytes do not predict compressed Tape capacity.

Restore keeps automatic File/directory selections distinct from explicit FileVersions. The creation dialog chooses latest saved content or the latest recorded backup at or before a local date/time. Automatic rows follow that policy; custom versions remain fixed. **Change version** or double-click opens a paged version picker with the selected content's Preview and copy availability. **Apply current policy to all** resets custom choices. Unmatched selections stay visible and block preparation until removed, changed or explicitly skipped for that cutoff; missing copies are a separate blocker and are never covered by the skip. Changing selections or the time policy invalidates skip consent. Waitlist selections and policy survive navigation within the browser session. The server owns [historical resolution](library.md#organization-and-content), directory expansion and frozen Job choices; this is not a historical directory snapshot.

Backup and Restore waitlist directories open inside the same pane, with parent/root breadcrumbs and paginated immediate children through Files.List. Browsing does not replace the selected roots, collect files, or execute filesystem actions. Removal applies to explicit rows at the waitlist root, not implicit descendants. Nested Restore files use the same version picker; custom choices are submitted alongside the directory root and replace that File's automatic version. The visible page resolves automatic versions against the global time policy; failed or superseded reads cannot restore stale child rows.

Generic workflow explanations belong in documentation, not persistent Job cards, Scan forms or Media read dialogs. Progress, results, required Media and recovery actions remain visible. Metadata editing and matching-file views use labels and data without repeating what tags, notes or independent Files mean; bulk-edit scope and safety warnings remain explicit.

Confirmations and name prompts use the application-owned [action dialog](../../frontend/src/components/action-dialog.tsx), not browser `alert`, `confirm` or `prompt`; lint enforces this boundary. Dialogs name the operation and target, retain destructive-action scope, and accept operation-specific content/options. Cancel/Escape does not execute the action; submission locks dismiss and repeat-submit controls, and failures remain in the dialog. A successful mutation followed by a refresh failure reports the refresh separately instead of inviting another mutation. Inline alerts and notifications remain appropriate for non-blocking feedback; browser unload protection is a separate platform capability.

Job creation must have a review surface before execution: Backup/Restore creation dialogs, Scan configuration, and Media read/write dialogs provide it through their target/options and final action button. Creation pages use their top tabs as labels, without redundant New headings or a Locations shortcut. Alerts share the form's vertical gap rather than independent margins. Bare integrity-check creation and retry shortcuts open a confirmation dialog first. Stop and delete also require confirmation. Navigation to a creation page, Properties, results or logs does not require confirmation or start a Job.

Presentation cleanup includes tracing response fields and server calculations to their consumers. Remove presentation-only data with no remaining business or client use through the protobuf generation path; retain fields used for validation, selection binding, content identity, pagination and actionable diagnostics. The selection-review API follows the [Library aggregate contract](library.md#visibility-and-selection), not a hidden output-path preview.

Backup and Restore waitlists use Chonky's optional `footer` slot for their creation-dialog entry action. One browser frame owns the outline, divider and outer corners; there is no separately rounded list inside another card. The list scrolls independently of its footer. Configuration scrolls inside the modal, with Cancel and final preparation in its action bar. The [shared component contract](../../frontend/patches/README.md) owns the extension and its source-build process.

Rows containing path or version details use content-measured heights in the shared virtual list, including after details change. Ordinary single-line rows remain compact. Waitlists omit a secondary path when it is identical to the displayed name.

Restore shows a compact destination path control. Its compact save-location dialog puts a preferred-Location selector above the live directory browser, compact breadcrumbs and **New folder / Cancel / Choose**. The dialog follows content height; only the directory list scrolls, without a fixed-height sidebar or empty space below its actions. Double-click enters a directory; Choose confirms the current directory. Re-selecting the current breadcrumb, including the root, is a no-op rather than a reload. New folder performs an immediate checked creation; Cancel does not undo it. Navigation and cancellation do not collect files or change Library. There is no preferred/all toggle or fallback; an empty preferred list links to Settings. Failed navigation clears old rows; a failed page resets pagination so Retry reloads the directory. Advanced damaged-copy recovery remains off by default. [Job indexing](jobs.md) freezes contents, logical targets, destination bindings and collision-safe outputs.

The target picker filters preferred Locations on the server before pagination; additional-page requests cannot overlap or append duplicate IDs. Closing the modal invalidates its pending responses. Only a confirmed choice is saved in browser-local storage, including Location ID, binding token and relative directory. Returning to Restore reloads that Location and reuses the choice only if it remains preferred, locally confirmed and bound to the same token. Deleted, rebound or ineligible targets require selection again; a late lookup cannot override a new choice. Cancel leaves the prior choice intact. This is a browser preference, not a change to CLI destinations or server write authorization.

All creation results, Jobs rows and related-object histories link to the canonical `/jobs/:id` detail. Returning to Jobs preserves filters, loaded pages and list position. The same detail component owns progress, results, logs, cancel/retry and storage actions. Read dialogs offer only the kinds represented by required Media: a single-kind Job opens directly on that kind, and Verify displays its fixed Media identity rather than offering another backend. Restore with both kinds defaults to Volume and allows switching to Tape; Tape inspection must match a required identity before submission. Missing catalog Media is an error, not a fallback choice. Job creation is never presented as a finished backup or restore.

Job detail headers provide a **Jobs** back link with an arrow. This link, the top
**All** tab and sidebar **Jobs** navigate to the originating filtered list, or
`/jobs` for a direct detail link. Navigation tabs use route links so an already
selected tab still works; duplicate Library/All-jobs header buttons are absent.

Jobs filters use labeled, wrapping fields with explicit all-values and application-owned layout classes, independent of the MUI class-name prefix. Filters retain usable widths on narrow layouts rather than collapsing to truncated single-letter labels.

Related Jobs use compact type/status/date/result rows and a resource-filtered **View all** link. Jobs supports kind, persisted state, Location and Media filters before pagination; resource provenance comes from frozen selections and actual operations. Media actions are contextual: **Properties** inspects identity/capabilities, **Scan** configures content and inventory policies, **Add to Library** admits selected archive entries without copying bytes, **Check integrity** presets recorded-copy verification, and **View jobs** opens its history. Inventory and verification share SCAN progress and results; health observations remain independent of accessibility and Job completion. **Scanned folders** identifies either Location or Media ranges without inventing a Location for Media. Read-only result dialogs remain dismissible during loading and discard late responses after dismissal.

Media names stay separate from secondary capability/availability details so prompts and breadcrumbs identify only the target. Mounted Volumes start scanning directly; Tape requires its explicit device/read step and fresh LTFS inventory. **Add to Library** requires signed regular archive entries. Position details are labeled **Archived copies**, inventory deletion is **Remove from Library**, and **Clean up Library** explains its retention scope before execution. Single-Media operations reject multiple eligible selections with an actionable notice rather than silently doing nothing or choosing one. Context actions use Chonky's filtered action selection.

The [CLI](../../cmd/yatm-cli/files.go) covers shared Files queries/inspection/collection, organization, Scan policies and Library/Location-selected Archive. Analyze, Preview and Verify convenience commands create ordinary SCAN configurations, not separate services or runners. Permanent delete requires explicit CLI confirmation independently of the browser preference. The [Demo](../operations/demo.md) is a maintained review surface; [CLI E2E](../operations/e2e-test.md) provides executable acceptance. The [Alpha release notes](../releases/v1.0.0-alpha.1.md) identify the supported release and validation scope.
